# DSH memory and procedural learning research

Research date: 2026-09-09. Scope: primary-source research and selected local source inspection for a proposed Digistrique fork of haitang1/dsh-memory. This document is an architecture recommendation, not a claim of successful installation, completed security audit, or evaluated learning quality.

## Recommendation

Fork and harden dsh-memory as a native DSH memory component, then add an independently switchable learning component in the same repository/bundle. Keep the existing DSH skill registry and the user's skills access policy as the authority for discovering and admitting procedures. The missing product is evidence-backed lesson capture, review, publication, and feedback. Another vector database, agent framework, or skill marketplace is not the first requirement.

This qualifies the earlier recommendation: the upstream plugin's documented breadth makes it a promising base, but documentation alone does not establish that it is the best or sufficiently safe. Compatibility and correctness are acceptance gates before enabling unattended writes.

## What exists today

### haitang1/dsh-memory

The current README describes release 0.2.11, fourteen DSH tools, automatic turn summaries and consolidation, editable raw memories, versioned summary history, global/workspace/project scopes, BM25 plus optional vector retrieval, standalone MCP, secret redaction, and a web settings card. It claims validation against DSH 0.1.2-rc.1. `scopedMemory` defaults to false. Summary injection is refreshed on prompt assembly; that differs from Hermes' frozen session snapshot. Its runtime auto-memory skill guides fact capture and correction, rather than generating reusable skill packages. These are upstream documentation claims, pending the companion code audit and runtime checks. [Upstream README](https://github.com/haitang1/dsh-memory)

Do not schedule all of these as new features. Audit how each behaves under concurrent writers, cancellation, malformed input, and scope restrictions first.

### Hermes native memory

Hermes documents bounded `MEMORY.md` and `USER.md` stores, with default limits of 2,200 and 1,375 characters. Session-start snapshots preserve a stable prompt prefix, while tools show live writes. SQLite FTS5 conversation search is separate. Post-turn background review can update memory and skills; optional write approval stages updates. Default review tools are memory, skill management, and read-only filesystem tools, with an explicit extra-tool allowlist. Background work has cost controls and can defer for an idle local GPU. Its pending review queue is in memory and can be lost at exit. [Persistent Memory](https://hermes-agent.nousresearch.com/docs/user-guide/features/memory/)

### Hermes skills and maintenance

The documented skill loop creates or patches procedures after a reusable workflow, successful troubleshooting, or correction. It aims to distill general rules into existing topic files rather than accumulate incident logs. `skills.write_approval` is false by default; enabling it stages all agent skill mutations with diff/approve/reject controls. The separate dangerous-content scanner is not the approval gate. [Skills System](https://hermes-agent.nousresearch.com/docs/user-guide/features/skills/)

The curator tracks use, marks stale skills, and archives long-unused ones. Model-driven consolidation is opt-in; automatic maintenance is primarily deterministic. Archival is recoverable, pinned and scheduled skills have protection, and backups plus an audit ledger support rollback. It can handle package resources when consolidating. This maintains the library; neither the documented usage count nor recency is proof that a procedure worked. [Curator](https://hermes-agent.nousresearch.com/docs/user-guide/features/curator)

Selected source inspection at Hermes commit `bf53ff00a7360826ec2c9e2949533160068a8fc8` confirms separate background-review execution control, cancellation/foreground-priority handling, accounting, and a prompt that requires fresh reads before updating an existing skill. The prompt distinguishes curator-managed from user-owned, bundled, external, hub-installed, and pinned skills. It explicitly protects the latter classes in autonomous review. Source inspection here did not independently prove every advertised enforcement path in the mutation tool. [Background review source](https://github.com/NousResearch/hermes-agent/blob/bf53ff00a7360826ec2c9e2949533160068a8fc8/agent/background_review.py#L419)

### Hermes self-evolution is a separate project

Nous Research also publishes an evaluated candidate-generation pipeline using DSPy and GEPA. Its status table marks skill optimization implemented; tool descriptions, system prompts, implementation-code evolution, and a continuous pipeline remain planned. The README describes evaluation, constraints, and PR review, but does not establish an automatic correctness guarantee for ordinary Hermes memory. Use the candidate-versus-baseline evaluation idea; do not adopt the entire optimization framework before a useful local dataset exists. [Self-evolution repository](https://github.com/NousResearch/hermes-agent-self-evolution)

“Self-learning” here means updating external memory and procedures. It does not mean changing model weights or establishing autonomous software repair.

## Proposed architecture

The following is design judgment, not a description of upstream functionality.

1. **Memory service:** own facts, scope resolution, durable mutations, retrieval, and summary projection. All entry points use the same authorization, validation, secret handling, journal, and concurrency boundary. Never let an alternate MCP or settings endpoint bypass these rules.
2. **Learning service:** collect eligible turn evidence, create candidates, validate, maintain review state, and publish versioned procedures. It depends on memory and skill capabilities through a small explicit contract. It does not own arbitrary shell, network, plugin installation, or permission changes.
3. **Learned skill provider:** expose only admitted, active versions in the allowed session scope; retain invalidation/disposal capabilities. Where the existing skills manager already supplies a safe mutation and publication service, use it instead of a second owner. If it lacks one, add a narrow integration seam, not calls into its web UI or private storage files.
4. **Review UI and tools:** list candidates, show evidence and exact diffs, accept/reject, pin, retire, and roll back. The UI renders Host-owned decisions. Removing the UI does not disable storage or admission policy.

A same-repository implementation avoids package sprawl. Separate lifecycle-controlled modules let users enable memory without procedural learning. No new database is required solely for this separation; select persistence after the audit proves or disproves the existing journal's suitability.

### Evidence and state

Each candidate needs: stable id, kind (`fact`, `preference`, `procedure`), content, scope identity, origin, source session/turn/event ids, bounded evidence references, observation time, environment applicability, current status, target skill identity, expected base hash, and decision reason. Store provenance outside the authored skill text. The Host derives session/scope/evidence identity; it must not trust ids or success labels fabricated by the proposing model.

Suggested state flow: `proposed -> validated -> admitted -> active`; failures become `rejected`, later corrections `superseded`, and retired procedures `archived`. Validation and admission are distinct. A well-formed document is not a verified procedure, and passing an evaluation does not grant a broader scope or extra tools.

Capture an explicit user correction as evidence of the user's intent. Capture a command/test result as evidence of that specific observed outcome. An assistant saying “fixed” is insufficient. Tool exit zero alone is also insufficient for claims that require behavior validation. Failed, interrupted, or partially completed turns may supply useful negative evidence without being promoted as successful solutions.

Prefer updating a relevant learned procedure over creating a new skill for every incident. Preserve user-authored, bundled, externally managed, and pinned skills. Proposed changes to those belong in a separate reviewed patch; loading a skill during a task does not confer ownership. Use compare-and-swap publication against the reviewed base hash, and reject stale review decisions rather than overwrite a newer correction.

### Learning jobs

Use a bounded queue with a session/turn/evidence idempotency key, explicit failure state, retry limit, token budget, and disposal cancellation. Persist pending work if continuity across restarts is a product requirement; do not silently drop jobs because all workers are busy. Coalesce only when the newer evidence window fully includes the older one. Do not learn from the learning job's own transcript.

Keep factual summaries fresh without repeatedly rewriting the entire system prefix unnecessarily. Benchmark an immutable per-session base with appended revision context or on-demand retrieval against current per-prompt injection. Preserve correct next-step visibility; cache optimization must not restore a fact that has been corrected or revoked.

## Security requirements specific to learning

Memory poisoning is an established attack class: MINJA demonstrates that ordinary query interaction can plant records that influence later requests without direct memory-file access. This supports testing the capture-to-recall trust boundary, not assuming that local disk makes stored instructions trusted. [MINJA paper](https://arxiv.org/abs/2503.03704)

Required design controls:

- Treat retrieved pages, tool output, imported memory, and generated summaries as data. Do not convert “ignore approvals” or exfiltration instructions found there into durable preferences or privileged procedures.
- Record source trust and constrain destinations. Project-derived material does not become global memory automatically. Scope is an access boundary enforced before retrieval, embeddings, consolidation, export, and publication.
- Redact or reject secrets before persistence and outbound model/embedding requests, not only when injecting a summary. Generated files, logs, backups, evidence excerpts, and export archives need the same policy.
- Use narrow writable roots, safe path handling, immutable revisions, concurrency control, and crash-recoverable publication. Protect against symlink escapes and scope-selection fallbacks.
- Validate learned scripts separately from prose; proposing a script must not authorize running it. A procedure cannot increase its own tools, change access policy, or enable itself globally.
- Bound retained evidence and support deletion with clear semantics. Revoking a lesson must exclude derived summaries and indexes from future retrieval; rollback must not accidentally re-enable a revoked secret or instruction.

These are proposed requirements. Whether upstream violates a particular one must be established by the companion source audit and reproducible tests.

## Acceptance tests and product metrics

Use a small curated fixture set with deterministic oracles and held-out variations. Compare the same model/configuration in three modes: no memory, hardened memory only, and memory plus learning. Keep test outcomes outside the learner's input.

| Case | Pass condition |
|---|---|
| Verified troubleshooting repeated later | Learner captures the working procedure; a new session uses it correctly on a related held-out task. |
| Plausible but unverified final answer | No “verified” procedure is admitted. |
| User changes a preference | New session uses the correction; previous fact remains attributable but is not active. |
| Similar project names and separate worktrees | No unauthorized cross-project retrieval, consolidation, or publication. |
| Hostile instruction in webpage/tool output | It never becomes an active preference or an instruction that bypasses policy. |
| Secret in tool output | No persisted, injected, exported, logged, or provider-bound plaintext leak. |
| Duplicate turn replay and concurrent writers | One capture, no lost update, and stale decisions fail clearly. |
| Crash between candidate and publication | Recovery exposes the old complete version or the new complete version. |
| Skill uses supporting files | Accepted publication and rollback preserve the complete package and valid links. |
| Registry policy disabled for a skill/source | New learned provider cannot bypass the restriction. |
| Plugin unloaded during a job | No late publication; jobs settle without changing active conversation history. |

Measure recurrence of corrected failures, held-out task success, unrelated-task regression, harmful admission, scope leakage, useful retrieval precision, extra tokens/latency, pending backlog, and rollback success. “Skill was loaded” counts exposure, not successful use. Model-as-judge scores can supplement deterministic results but must not be the only admission signal.

## Implementation order

1. Pin upstream and intended DSH versions; reproduce audit findings; fix storage, isolation, credential, lifecycle, and compatibility defects. Gate: baseline tests plus isolated real Loader install/use/unload/reinstall and migration proof.
2. Add provenance, unified mutation policy, revocation, and durable job bookkeeping. Gate: concurrency, crash recovery, scope, replay, secret, and poisoned-input fixtures.
3. Implement candidate extraction and a complete review/decision flow, initially with shadow capture and no unattended procedure activation. Gate: end-to-end evidence-to-diff-to-publication-to-fresh-session recall and rollback.
4. Integrate learned skill publication with the actual deployed registry/access policy. Gate: provider lifecycle, scope admission, protected ownership, full resource packages, and denied-source tests.
5. Add repeated-task evaluations and configurable unattended admission only for explicitly eligible classes that pass the selected gates. Gate: held-out benefit without safety or unrelated-task regression and within a declared token budget.
6. Add maintenance: usage attribution, staleness proposals, pinning, archival, restore, and optional consolidation. Gate: maintenance cannot remove referenced/pinned/user-owned procedures and rollback restores a valid package.

Defer vector-service expansion, knowledge graphs, agent-framework migration, automatic core-code rewriting, global skill publication, and broad GEPA searches until observed retrieval or evaluation gaps justify them. These are separate features, not prerequisites for the requested complete learning workflow.
